## [Unreleased]

### Added

- A trivia streak keeps the category it was asked for (`trivia_chains`): the rounds that follow on their own stay in it until the streak ends, instead of going back to the whole pile. A plain `!trivia` asks for anything again.
- `!banderas` (alias `bandera`), a flags round of the trivia: which country a flag belongs to. A category of the trivia and not a game of its own, so it already answers to a bare letter, chains and pays into the same ranking. The questions are made out of `app/data/flags.json` and the flag is not stored -- a flag emoji *is* its ISO code -- and the wrong answers come from the same continent, which is what makes it hard.
- What Tox remembers about the people of a chat from talking to them (`services/person_memory.py`, `person_notes`, `!memory`, `!config memory`, `CLAUDE_MEMORY`, `CLAUDE_MEMORY_MAX_NOTES`, `CLAUDE_MEMORY_MAX_CHARS`). No extra question is asked for it: the answer Claude is already giving ends with `[memoria] Nombre: dato` lines, which are taken off before the chat sees a word of it and stored. The block is asked for on every answer, with `[memoria] -` to say nothing came up: asked as a favour it was simply never added, and an answer that comes back without it is logged as not having followed the request. The stripping is greedy on purpose, since the one failure that matters is a marker reaching the chat. There are two kinds, because people are not the same thing as groups: `[memoria global]` is what somebody *is* and is read in every chat they are in, while `[memoria]` belongs to the group it was learned in and never leaves it, each with its own ceiling. The personal mode is never learned from and only a group is learned from -- a group is people talking and the admins are people in it like anybody else, while a private chat is one person driving the machine with no group to know -- a name has to be somebody who is in that chat or the note is dropped -- read loosely, since what the model writes is what it read in the conversation and not a display name ("Leandro" is the member WhatsApp calls "Leandro 1899"), but never when two members could be meant, and `!memory` reads anybody's -- your own with no name, somebody else's by name or by tagging them, read generously ("Lean" is "Leandro 1899") and asking which one when more than one person answers to it, since these are notes about the people of a chat taken from what was said in front of all of them. Deleting them (`!memory forget`, every note about somebody in every chat) is with the admins while the feature is new: what it learns is still being watched, and a note that is gone cannot be looked at to see why it was kept. A chat turns it off with `!config memory off`, and the notes read back into the prompt sit in the untrusted block with the conversation, never in the owner's own description of the chat.

### Changed

- When Tox says something nobody asked for, a table of objections decides it in code before Claude is called (`services/discretion.py`): nothing outside the hours it talks in, after two remarks nobody answered, once it has written more than twice what the average person there has, while the chat is talking about something heavy, or while a trivia round is open. A dice roll keeps a remark rare; these keep it welcome. Each objection is a function over a snapshot of the chat, and the first one that answers is both the decision and what gets logged (`CLAUDE_INTERJECT_START_HOUR`, `CLAUDE_INTERJECT_END_HOUR`, `CLAUDE_INTERJECT_SHARE_LIMIT`, `CLAUDE_INTERJECT_PATIENCE`).

## [1.0.0] - 27 Oct 2026

### Changed

- Trivia answers no longer need the prefix: a message that is just `a`, `b`, `c` or `d` answers the question this chat has open, typed on its own or as a reply to the bot's question, and `!a`...`!d` still work. Read before anything else, so a letter replying to the bot is an answer and not a question for Claude. Only while a round is really open, and never in the personal mode, where the bot writes as the owner and a stray letter must not become a move in a game.
- A trivia round that ends starts the next one on its own, whether it was won or the time ran out, as long as somebody did answer it; a question nobody answered ends the streak and the chat is left alone. A win chains inside the reply that announces it, while a timeout has nobody typing to answer to: `trivia_service.queue_due` turns it into pending alerts on the bots' own poll (like reminders), which also means a timeout is finally announced without anybody having to type.
- 72 new trivia questions (144 in all), harder than the ones that were there: science, history, culture, video games, geography, sport and Uruguay. `TRIVIA_TIMEOUT_SECONDS` is 30 (was 60).
- `claude` answers can be twice as long: `CLAUDE_MAX_ANSWER_CHARS` is 800 (was 400), and the voice notes take 500 characters (was 300), `!voz` included. Both limits go into the prompt and are enforced afterwards -- the answer is still cut to `CLAUDE_MAX_ANSWER_CHARS`, and one that does not fit in a voice note is still sent as text. The prompt for a spoken answer now asks for `SPOKEN_SLACK` (20) characters under the voice limit instead of a number of its own, so the two can no longer drift apart.
- What the chat profile says about each member reaches Claude only `CLAUDE_PROFILE_PEOPLE_CHANCE` of the time (0.25) when nobody typed a command -- a remark of its own, or an answer to a reply -- so it stops making the same joke about somebody's job or city every time it opens its mouth. The chat's own description always goes, and a typed `!claude` still gets everything.
- `chats.json` can tell the elementary facts of a person apart from the rest: `"Nombre": {"basics": "34 años, vive afuera", "about": "..."}`. The `basics` go to Claude every time it speaks; the `about` is what the dice above decides. A person written as a string or a list is all `about`, as before.
- `start_dev.sh` only reinstalls the dependencies when `requirements-dev.txt` is newer than the last install (a service that restarts on failure must not reach the network every time), `exec`s uvicorn, so a stop signal reaches it directly, and no longer passes `--reload`: it is what the systemd service runs, where a reloader only adds a process watching files nobody is editing.
- When a `claude` (or `res`) answer arrives the `⏳` reaction is taken off instead of being replaced by a `✅`: a reply with an empty `reaction` now means "revoke the reaction you left there" (`null` still means "leave them alone"). `⚠️` is still used when there is no answer.

### Added

- Release notes the chats are told about on their own (`app/data/news.json`, `services/news.py`, `news_states`, `!novedades`): when a feature ships, its note goes out to the same chats the alerts and the GTA countdown go to, on the bots' own poll, so a deploy and a restart are all it takes. The note is written by hand in Spanish, for the group to read, and ships in the commit of the feature it announces -- the CHANGELOG is in English, technical and long, and nobody in a chat reads that one commit at a time. It names the versions it released (`whatsapp-bot 1.0.0`, `api-core 1.0.0`), written in the entry itself because the API cannot see the bot's `package.json` and a number copied into a setting drifts from the release it meant to name. What is remembered is the id of the newest entry already queued, not when it went out, so a restart announces what is new and never the same thing twice; the first run on a machine announces nothing and only writes down where the file stands, the same rule the countdown follows. At most three go out together, an entry missing its id or its text is skipped and logged instead of being sent half-written, and `!novedades -probar` (admins) shows what is about to be announced, to how many chats, before a group reads it.
- `!yt <link>` sends the video of a YouTube link into the chat, `!ytm <link>` only the audio (`services/youtube.py`, yt-dlp + ffmpeg; `YT_MAX_DURATION_SECONDS`, `YT_MAX_BYTES`, `YT_TIMEOUT_SECONDS`, `YT_WORK_DIR`, `FFMPEG_PATH`). The link may also be in the message being replied to, and both answer with a ⏳ and a job, like `!claude`. Nothing is kept on this machine: the download is written into a temp folder inside `YT_WORK_DIR` (`/dev/shm`, RAM, so an eMMC with little room left is never touched), read, and the folder deleted before the reply is built; from there the bytes live in `media_cache` only until the bot has fetched them. A video needs that folder because YouTube no longer serves one stream with picture and sound in it -- yt-dlp downloads both and ffmpeg merges them, which it cannot do into a pipe. Two limits, both read off the metadata before anything is downloaded: eight minutes, and 16 MB over the formats on offer, where the quality is stepped down (720p to 240p) until picture plus sound fit, because eight minutes at 360p is about 24 MB; what does not fit even at 240p is refused with a message instead of failing halfway up an upload. Only H.264 and AAC are picked, so the merge is a remux and nothing is ever re-encoded on this machine. One download at a time, and lives, playlists and videos that are private, age-restricted or members-only are each refused in their own words. `yt-dlp` is in `requirements.txt` rather than the system's one so dependabot keeps it current: YouTube breaks old versions every few months.
- A reply can carry a video (`Reply.video`, `GET /api/v1/videos/{id}`, `sendVideo` in the bot): the biggest thing the bot ever fetches, and the first media the API serves that it did not draw itself.
- `OWNER_USER_IDS`: whoever is listed there is an admin in every chat, including a group somebody else runs where WhatsApp does not make them an administrator -- until now the owner was a plain user in such a group and `!res`, `!h` or `!service` were refused there. Everybody else on `ADMIN_USER_IDS` still needs to administer the group they write in. Being on the owner list is enough on its own, and the personal mode is still never admin.
- `!spy` (admin only, alias `espiar`) names chats (`chat_aliases`: one word per chat, `-alias`) and decides which chat may be told about which, always from the chat that is going to read: `!spy festejen risas,asado`, `!spy -off festejen`, `!spy -list`. An alias grants nothing by itself; the permission is the row, and it is written in one direction only.
- A chat can be told what was said in **another** chat (`chat_context_sources`, set up with `!spy`; `CLAUDE_SOURCE_MESSAGES`, `CLAUDE_SOURCE_MAX_CHARS`). A row is one direction -- A reading B does not let B read A -- and it is read only when the question names one of the row's `triggers`: any other question is answered as if the source did not exist, and nothing of that chat reaches the prompt, which is a stronger control than asking Claude not to mention it. A remark Tox makes on its own has no question, so it never brings another chat up. The prompt calls the source by its `label`, not by the group's real name, and is told to use it without copying messages verbatim; those people are not in the chat and are never taggable. A question that calls a source up is answered in the no-access mode even for an admin: the full-access mode receives nothing written by other people, and asking what was said somewhere is a question about a conversation, not about this PC -- without that, an admin could never see a source in their own group, since being an admin is what puts them in the other mode.
- A chat can be given its own tone (`!config tono salado | picante | tranqui | normal`): `CLAUDE_TONE` joins the whitelist of `!config`, and the tone the chat asked for travels to the prompt of both modes and of a remark of its own (`claude_runner.start(..., tone=...)`). What the `.env` says is still the tone of every chat that was never configured. New `tranqui` tone: playful and joking, but it teases nobody -- the joke is about the situation or about itself, never about somebody's defects, failures or looks, and there is no swearing, black humour or sexual joking. It is what a group where not everybody is in on the joke wants, where `salado` would insult people who never asked for it.
- `-no` at the head of a reply to one of the bot's own messages: nothing is answered, because that reply was for the people in the chat and not for Tox. In a group most replies to what the bot said are people talking to each other, and every one of them used to get an answer nobody asked for (`CLAUDE_ON_REPLY`). Claude is never called, so it costs nothing and uses no question of the hour, and nothing is sent or reacted to. Only read where no command was typed -- `!claude -no sé qué hacer` is still the question it looks like -- and it combines with `-t` in any order.
- `!config` (admin only, alias `conf`): how talkative Tox is **in this chat**, instead of one number for every chat read from the `.env` at startup. Seven settings can be given a value of their own per chat (`charla`, `espera`, `perfiles`, `respuestas`, `audio`, `contexto` and `horas`, which are `CLAUDE_INTERJECT_CHANCE`, `CLAUDE_INTERJECT_COOLDOWN_MINUTES`, `CLAUDE_PROFILE_PEOPLE_CHANCE`, `CLAUDE_ON_REPLY`, `CLAUDE_AUDIO_CHANCE`, `CLAUDE_CONTEXT_MESSAGES` and `CLAUDE_CONTEXT_HOURS`); `!config` lists them with where each value comes from, `!config charla 15%` sets one here only, `-reset` drops it back to the general one and `!config -off` / `-on` stop or resume it butting into this chat. A chance is read and written as a percentage, a yes/no as `sí` / `no`. Rows live in `chat_settings` and survive a restart, so these never need the `.env` touched again; what the `.env` says stays the default for every chat that was never configured, and there is deliberately no way to change that default from a chat. The settings it may touch are a whitelist (`chat_config.OVERRIDABLE`) -- an admin typing into a group reaches this code, so a key, a path or a money cap must not be reachable from a message -- and each value is validated by the field's own type and `ge`/`le` in `config.py`, so a chat cannot be given a number the `.env` itself would have been refused for. A stored value that stops being valid is ignored in favour of the general one rather than breaking the chat.
- The GTA VI countdown is sent as a card instead of a text message: a picture of the game over a bar with the days, hours, minutes and seconds left. The picture is one of `GTA_ARTWORK_DIR` (`media/gta6`, not tracked) at random, read from disk every time, and the day it comes out it is always `GTA_COVER_FILE`. With no readable picture there the card draws its own Vice City sunset. The card is square on purpose: WhatsApp on iOS crops a preview taller than about 1:1, and the first 720x898 one lost its numbers off the bottom of the bubble. The text message stays as what the bot sends when it cannot fetch the card, so a drawing can never cost the message.
- A proactive alert can carry an image (`pending_alerts.image`, `GET /api/v1/alerts/pending`): the bot sends the picture and falls back to the row's text when it cannot fetch it. It is what the countdown card rides on, and the first thing in that queue that is not plain text.
- The same countdown, published as an Instagram story at every one of its moments (`INSTAGRAM_ENABLED` and the three settings around it, `app/services/instagram.py`): the card laid out 1080x1920 over its own artwork, blurred and darkened. The account has to be a professional business one, since a creator account cannot publish stories. Instagram downloads the picture from a public URL rather than receiving it, so it is parked on imgbb and deleted again right after. The container is only published once its `status_code` reads `FINISHED` -- publishing one Instagram is still fetching is refused with "Media ID is not available". It runs in a thread of its own and can never fail the countdown: whatever goes wrong is logged and the chats get their message anyway.
- A countdown to Grand Theft Auto VI (19 November 2026, 00:00 Uruguay time): `🌴 Falta mm:dd:HH:MM:SS para Grand Theft Auto VI 🦩`, sent on its own to the same chats the alerts go to, once a day at midnight and every hour over the last four days (from 15 November). The day it comes out, one last `🌴 Bienvenidos a VICE CITY. 🌴` and the countdown is over for good. `!vi` (`!gta6`) asks for the same message by hand, in the chat it was typed in, so it works in the personal mode too (`.b vi`). No background thread: it rides the poll the bots already make for pending alerts, and `countdown_states` remembers the scheduled moment already sent, so a late poll still sends it and no moment is ever sent twice.
- `!claude -t <pregunta>` (`!c -t ...`, `.b c -t ...` in the personal mode) answers as text for certain, instead of leaving it to `CLAUDE_AUDIO_CHANCE`: the dice is not thrown at all. It is for everybody, not only the admins, it combines with `-n` in any order, and it is read when replying to a message of the bot too, where there is no command to write a flag on. Without it nothing changes, and a question that merely starts with a dash is still asked as typed.
- `!censura @usuario` (admin, groups only): a switch that makes the bot delete every message that person sends in that group, their commands included, until the same command lifts it. It is per chat, and anybody can be censored except the bot and whoever runs the command (a group admin and a listed admin included: nobody leaves the group and the same command undoes it). The API only keeps the list (`censored_users`) and serves it at `GET /api/v1/censored`; the bot reads it and deletes on its own, which is the only way it reaches the messages the API never sees (ordinary chatter of a group with history off). The bot has to be an admin of the group.
- The log is written to a file besides the console: one per `LOG_ROTATE_HOURS` (24 by default, rolled over at midnight) in `LOG_DIR` (`logs/`, git-ignored), as `tox.log` plus `tox-2026-10-20.log` for the days gone by. uvicorn's own lines (startup, the access log) go to the same file. Nothing is deleted automatically: old files are removed by hand. `LOG_DIR=` (empty) keeps it on the console only, which is what the tests do.
- `start_test.sh`, the API while writing code: the same thing as `./start_dev.sh` (dev, `.env`, `requirements-dev.txt`) with uvicorn's reloader on, so every save restarts it.
- `tox-core.service`, a systemd user unit running `./start_dev.sh`, documented in the README (the unit itself lives in `~/.config/systemd/user/`, outside the repo).
- `claude` butts into a conversation now and then (`CLAUDE_INTERJECT_CHANCE`, 0.02 of the messages, `CLAUDE_INTERJECT_COOLDOWN_MINUTES` between remarks): in a group whose history is on it reads what is going on and sends one remark of its own, always as text, always without access to the PC and signed with a `> Tox` line. Claude decides whether it is worth it at all (`paso` sends nothing), and everything about it is silent: no reaction, no busy or limit message. The bot now forwards ordinary chatter of those groups (without downloading its pictures), which is what makes it possible.
- Replying to a message of the bot asks `claude`, with no command typed (`CLAUDE_ON_REPLY`, on by default): the whole reply is the question and the answer continues the thread. A reply to a voice note counts too, and the personal mode is left out (there the bot writes as the owner). The question is not saved to the history twice, since the bot already saves everything that is not a command.
- `claude` answers are sent as a voice note `CLAUDE_AUDIO_CHANCE` (0.25) of the time, in `CLAUDE_AUDIO_VOICE` (`!voz -h`'s voice). Decided before asking, so a spoken answer is asked for short and tagless; it falls back to text when it tags somebody, is too long or the voice service fails.
- Per-chat profile for `claude`: `CHATS_FILE` (`chats.json`, git-ignored, `chats.example.json` tracked) holds each chat's `name`, `about`, `people` and `notes`, read on every call (`app/services/chat_profiles.py`) and handed to both modes as the owner's own description of the chat (the rest of the context stays untrusted data).
- `claude` context: `CLAUDE_CONTEXT_MESSAGES` is 150 by default and `CLAUDE_CONTEXT_MAX_CHARS` (20000) bounds it; `CLAUDE_PUBLIC_MAX_BUDGET_USD` is 0.10. In a chat with the history on, every `!claude` exchange (the question and the answer sent to the chat, admin or not) is saved in it (`claude_context.remember`), so the no-access mode keeps the thread whoever asks. The admins' CLI session stays separate and never reads others' text.
- `claude` no longer answers "Ya hay una consulta en curso": questions wait their turn (`CLAUDE_PARALLEL` no-access questions and summaries at once, the admins' full-access ones one by one, `CLAUDE_QUEUE_MAX` places in line; `Busy` only when it is full). New `CLAUDE_TONE` (`salado` by default; `picante`, `normal`): the no-access prompt insults and swears like the friends do, with a few explicit limits.
- `claude` has the context of the group: the names of the members (`USERS_FILE` first), the message it replies to (new `quoted` field on `POST /api/v1/messages`) and, without PC access and only where the history is on, the latest `CLAUDE_CONTEXT_MESSAGES` messages of the last `CLAUDE_CONTEXT_HOURS` hours (`app/services/claude_context.py`). The no-access prompt now speaks as one more member of the group, and an `@Name` in the answer becomes a real mention. The admins' mode never gets the conversation. `!c <question>` is an alias when there is a question (`!c` alone stays the trivia answer). `chat_history.transcript` is shared with `res`.
- uvicorn's own log lines (startup, the access log) now carry the date and time, like the app's (`timestamp_uvicorn_logs` in `app/main.py`).
- Chat history: `h -on | -off | -status | -delete` (alias `historial`; `owner_only`: from the owner's personal bot or by an admin through the groups bot, refused with 🚫 and unlisted for anyone else) saves the text of a chat to a SQLite file of its own (`HISTORY_DB_PATH`, git-ignored; oldest messages deleted past `HISTORY_MAX_MB`), and `res [-today | -all | 6h | 2d | 150]` (alias `resumen`; today's messages by default) has Claude summarise it (`claude_runner.execute_summary`, no tools, own money cap). New `GET /api/v1/history/chats` and `POST /api/v1/history`, `chat_aliases` on `POST /api/v1/messages`, and the `history_chats` table.
- `personal` field on `POST /api/v1/messages`, set by the WhatsApp bot's personal mode (the owner's own number, private chats): commands there start with `.b ` (`.b sticker`, replies show that prefix), the sender is never treated as an admin, and `recordar` is refused (the groups bot would deliver it to that chat from its own number).
- Initial FastAPI scaffold: settings (`.env` / `.env.prod` selected by `APP_ENV`), SQLite database, API key authentication (`X-API-Key`), `/health`.
- `POST /api/v1/messages`: platform-agnostic entry point the bots forward chat messages to.
- Command framework with decorator-based registry, `!` and `/` prefixes, aliases and an auto-generated `!help`.
- Commands, all in Spanish: `ayuda`, `id`, `chiste`, `dado`, `elegir`, `m`, `uuid`, `base64`.
- Developer tools: `hash`, `url`.
- Jokes are general only (general, dark and spicy); no programming or gaming jokes.
- `m`: asks `y tu mamá donde está?` and mentions a random chat member other than the sender.
- Replies can carry `mentions` (`{@0}` placeholders) and messages can carry the chat's `participants`; users seen in a chat are remembered as a fallback member list.
- `m` also sends a random audio from `media/m` (`AUDIOS_DIR`, `M_AUDIO_PROBABILITY`); skipped when the folder is missing or empty. `GET /api/v1/audios/{name}` serves the clips to the bots; `media/` is git-ignored.
- `m` never repeats the same audio twice in a row in a chat (last audio remembered per chat in `last_audios`).
- `mute`: toggles whether the sender can be tagged in the chat. Muted users are excluded from `m` and any future tagging command (`taggable_members`).
- `service` (admin only): shows whether the hosted services and databases (Postgres, key-value) are up, or one in detail (status, region, last deploys, panel link, database expiry), using the provider's read-only REST API (`RENDER_API_KEY`). Names matching several resources list them all. The detail also shows memory and CPU of the last hour (provider metrics API; 💤 when there are none, i.e. probably asleep), only the last 2 deploys, and each deploy ends with a short local date and time.
- `service -L` (admin only): query (default), start (`-up`) or stop (`-down`) the local services of this PC from an allowlist (`services.json`), without a shell, with a timeout and an audit log entry per action.
- `service -L <name>` shows a detailed status when the service defines `info` / `last_usage`: since when it is up or down, memory, CPU (now, average, total) and the last run's usage. A stopped service now shows 🔴.
- `service -L` with no service name prints a one-line usage instead of listing the services. An unknown name reports configuration problems of `services.json`, if any.
- `service -L host` (or `master`): read-only report of the machine the API runs on: uptime, CPU (load, per-core usage, model, frequency, thermal throttling), temperature, memory, swap, disks, battery (level, plug, health, autonomy or time to full), biggest memory users, failed units, pending reboot and remote sessions. A background sampler (`HOST_SAMPLE_INTERVAL_SECONDS`, `HOST_HISTORY_DAYS`) records vitals in `host_samples` to show peaks and battery trends.
- `github` / `gh` (admin only): open PRs (`-r`, the default) or issues (`-i`) of one repo of `GITHUB_REPOS` (a name or part of it; a repo is required, `!github` alone prints a usage helper). PRs show author, assignees, days open, commit count, draft/open, head → base branch and link, most days open first; issues show number, title and assignee. Read-only GitHub REST calls; private repos through `GITHUB_TOKEN` or the `gh` CLI session (`GITHUB_TOKEN_FROM_GH`).
- Admin-only commands are hidden from `ayuda` for non-admins.
- Admin support: `ADMIN_USER_IDS` setting, `@command(admin_only=True)`, and `!id` shows the caller's role.
- Multiplayer trivia game (`trivia`, `responder`, `ranking`) with 72 questions in 7 categories (general knowledge, Uruguay and games) and a per-chat leaderboard.
- `sticker <texto>`: generates a meme-style sticker (512×512 WEBP, Pillow) with the given text. Fully in-memory, nothing written to disk.
- `voz [-h | -m] <texto>`: says the text out loud with Microsoft Edge's free neural voices (`edge-tts`; `-h` a man's voice, default; `-m` a woman's; both Uruguayan Spanish), converted to Ogg/Opus with `ffmpeg` so it plays as a real voice message on both WhatsApp and Telegram. Reuses `!m`'s `audio` field and `GET /api/v1/audios/{id}` endpoint, so the bots needed no changes.
- `media_cache`: a short-lived, in-memory (RAM only) store shared by `sticker` and `voz` for their generated bytes (`MEDIA_CACHE_SECONDS`); `GET /api/v1/stickers/{id}` and the `audios` endpoint's fallback serve from it. Nothing generated by either command is ever saved to disk.
- Test suite (pytest) covering the router, every command, the trivia rules and API authentication.
- Proactive alerts: a background monitor (`ALERT_SERVICES`, `ALERT_CHECK_INTERVAL_SECONDS`) checks local
  services (the same ones `!service -L` reads) and sends a message with no user command behind it — once
  when a service goes down, once more when it recovers, nothing on every check in between. Queued per
  destination chat (`ALERT_WHATSAPP_GROUP_JIDS`, `ALERT_TELEGRAM_CHAT_IDS`) in `pending_alerts`; each bot
  polls its own with `GET /api/v1/alerts/pending?platform=...` (fetch-and-delete, at-most-once delivery).
- The alert message includes the same extra detail as `!service -L <name>` (since when up/down, memory,
  CPU, restarts) when the service defines `info` in `services.json`.
- `risa`: sends a random laugh audio from `media/risa` (`RISA_AUDIOS_DIR`), reusing `!m`'s audio machinery
  (`audio_library`, `audio_picker`, `GET /api/v1/audios/{name}`) but with its own folder and its own
  per-chat "last sent" history, independent of `!m`'s.
- `uid` (admin only, hidden): prints the id and name of every user of the chat (plus the sender) in the API's log, as
  `platform:user_id — name | other ids` (phone number when WhatsApp shares it; a missing name is completed from the users
  the API has seen), ready to copy into lists like `ADMIN_USER_IDS`. It sends no message: the bot only reacts to
  the command with 👍. Needed a `hidden` flag on `@command` (not listed by `!ayuda`; non-admins get no reply at all) and a
  `reaction` field on replies, which both bots now understand.
